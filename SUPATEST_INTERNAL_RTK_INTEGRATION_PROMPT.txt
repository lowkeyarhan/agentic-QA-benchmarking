You are Codex working in the Supatest repository.

Goal:
Integrate RTK into the Supatest agent internally, so Supatest can use RTK as
part of its own shipped runtime/toolchain during benchmark runs.

Important benchmark fairness context:
- The benchmark harness hides host-installed `rtk` from agent subprocess PATH by
  default with `BENCHMARK_HIDE_HOST_TOOLS=rtk`.
- Do not depend on `/opt/homebrew/bin/rtk`, a globally installed `rtk`, shell
  rc files, or the benchmark harness to provide RTK.
- Do not add benchmark-only prompt instructions telling Supatest to use RTK.
- The intended behavior is product-internal: Supatest may use RTK because the
  Supatest runtime/toolchain includes it, not because the benchmark environment
  leaks it.
- Other agents should continue running with their own default CLI behavior.

Expected benchmark command after this work:

BENCHMARK_SUPATEST_BINARY=/Users/lowkeyarhan/Documents/supatest/cli/dist/index.js

The benchmark will launch that compiled local Supatest CLI. The compiled
Supatest runtime must be able to find and use its internal RTK integration even
when host `rtk` is hidden from PATH.

What to implement:

1. Inspect the Supatest CLI architecture.
   - Find the command execution layer used by the agent when it runs shell
     commands.
   - Find how the CLI is built into `cli/dist/index.js`.
   - Find packaging/build constraints for runtime assets, binaries, npm package
     files, and executable permissions.

2. Add an internal RTK resolver.
   - Create a small resolver module, for example `resolveInternalRtk()`.
   - It should prefer a Supatest-owned bundled RTK binary or Supatest-owned RTK
     executable path.
   - It must not rely on the user's global PATH.
   - It should return `null` or a disabled result when RTK is not bundled or not
     executable.
   - It should have clear diagnostics that say whether RTK is enabled, disabled,
     missing, or failed.

3. Decide how RTK is shipped with Supatest.
   Use the repo's existing packaging style. Prefer the least invasive option
   that works reliably after `pnpm -F @supatest/cli build`.

   Acceptable approaches:
   - Bundle an RTK binary under the Supatest CLI package, such as
     `cli/vendor/rtk/<platform>/rtk`, and ensure the build copies it into
     `cli/dist` or package output.
   - Depend on an internal Supatest package that provides RTK and exposes its
     resolved executable path.
   - If the repo already has a tool/binary asset mechanism, use that instead of
     inventing a new one.

   Avoid:
   - Calling `which rtk`.
   - Assuming `/opt/homebrew/bin/rtk`.
   - Mutating the benchmark harness.
   - Adding RTK requirements to fixture prompts.
   - Installing RTK globally during benchmark runs.

4. Route eligible shell commands through RTK.
   - Locate the shell command execution path used by the agent.
   - When internal RTK is available, execute commands through the internal RTK
     binary.
   - Preserve existing behavior when RTK is unavailable.
   - Keep command semantics the same: cwd, env, timeout, stdout/stderr capture,
     exit code handling, streaming, cancellation, and signals must continue to
     work.
   - Do not route the Supatest CLI process itself through RTK. RTK should wrap
     agent shell commands inside Supatest, not the benchmark's initial
     invocation of Supatest.

5. Add a runtime flag/config switch.
   - Default should be enabled only when internal RTK is actually bundled and
     executable.
   - Add an explicit opt-out for debugging, for example:
       SUPATEST_INTERNAL_RTK=0
     or an equivalent repo-consistent config name.
   - Add a clear log/telemetry field indicating whether internal RTK was used.

6. Preserve benchmark fairness.
   - Do not add shared prompt instructions about RTK.
   - Do not expose RTK to other agents.
   - Do not change benchmark fixture tasks.
   - Do not require the user to install RTK globally.
   - Do not depend on host PATH.

7. Add tests.
   Cover at least:
   - Internal RTK resolver returns the bundled executable when present.
   - Resolver returns disabled/missing when the bundled executable is absent.
   - Resolver ignores a fake global PATH `rtk`.
   - Shell command execution uses internal RTK when enabled.
   - Shell command execution falls back to normal execution when RTK is missing
     or disabled.
   - cwd/env/exit-code/stdout/stderr behavior is preserved.
   - Built `cli/dist/index.js` can still start.

8. Build and verify.
   Run the repo's normal checks, at minimum:
   - install if needed
   - typecheck/lint if available
   - focused tests for the command execution layer
   - `pnpm -F @supatest/cli build`
   - a smoke test that runs the compiled CLI from `cli/dist/index.js`

9. Provide a final summary.
   Include:
   - files changed
   - how RTK is bundled/resolved
   - how to disable internal RTK
   - verification commands run
   - any packaging caveats

Implementation notes:

  preserve argv-array semantics where possible.

- Keep the integration local to the command execution/tool runtime boundary.
- Prefer a small, auditable integration over a large abstraction.

- Do not break non-benchmark Supatest usage.
